## 1. Construction boundary

RI-PY receives an octet sequence and constructs a BC-02.1 receipt.

```text
issued artifact
      ↓
    RI-PY
      ↓
BC-02.1 receipt
```

The receiver does not determine conformance.

| Artifact | Path |

The receiver provides:

- the BC-02.1 logical receipt model;
- a closed handoff status domain (`HandoffStatus` enum);
- receiver-derived SHA-256 over received octets;
- fixture and provenance preservation;
- schema-level validation returning a complete per-assertion report;
- deterministic receipt serialization with an explicit Base64 octet transport;
- construction tests R-VAL-001…R-VAL-012.

Standard library only. No third-party dependency, and no dependency on any
RI-RS artifact.

## 3. Independence from BC-02.3

The only shared contract is BC-02.1. RI-PY does not import, wrap, vendor, or
transliterate the RI-RS implementation or its adapter. The decompositions differ
substantively:

| Concern | BC-02.3 (RI-RS) | BC-02.2 (RI-PY) |
|---|---|---|
| Receiver surface | free function `receive()` taking 13 positional arguments | `BoundaryReceiver` class; provenance bound once at construction, per-handoff surface is fixture + method + octets |
| Digest derivation | inline in the free function | private `_observe()` on the receiver instance |
| Validation model | `Result` returning the first error | full `List[ValidationResult]`; every assertion evaluated and reported |
| Octet transport | adapter-side, at the serialization boundary | in the receiver's own transport mapping |
| Text-input handling | not applicable to `Vec<u8>` | `str` explicitly rejected, so a hex or Base64 rendering cannot become digest input |
| Digest-parameter check | structural (signature takes no digest) | structural, plus `digest_input_is_caller_supplied()` making it testable at runtime |

## 4. Raw-octet rule

`BoundaryReceiver.receive()` accepts `bytes`, `bytearray`, or `memoryview` and
normalizes to `bytes`. SHA-256 is computed directly over that octet sequence.

The receiver MUST NOT use an expected digest, parsed object, reconstructed JSON,
textual hexadecimal representation, or Base64 characters as digest input. Two
structural guarantees enforce this:

1. `receive()` exposes no digest, hash, checksum, or expected-value parameter, so
   a caller-supplied digest cannot enter. `digest_input_is_caller_supplied()`
   inspects the signature and returns `False`, which R-VAL-005 checks.
2. `str` is rejected with `ReceiptConstructionError`. A textual rendering of the
   octets cannot be silently hashed as if it were the octets.

Base64 is a transport representation only; it decodes to the same octets before
any digest computation.

## 5. Receipt transport

BC-02.1 §12 serialization is implemented by `serialize_receipt()`: UTF-8,
lexicographic member order, compact separators, no insignificant whitespace, all
fields explicit, no `null`, and `raw_octets` carried as the declared Base64
transport encoding. `decode_transport_octets()` reverses that encoding, so the
representation is checkable rather than asserted.

Receipt encoding is not fixture representation. BC-02.1 was not modified to
accommodate this implementation.

## 6. Authority isolation

The RI-PY receipt type contains no `conformance_result`, PASS/FAIL result,
acceptance state, digest-output state, §4.5 result, or B-VAL-014 result.

`validate_receipt()` is a schema validation routine only. Its `ValidationResult`
entries indicate construction validity and are not conformance results.

Per AGENTS.md rule 4, no validation outcome relies on Python `assert`. Failures
surface as returned results or as `ReceiptConstructionError`.
